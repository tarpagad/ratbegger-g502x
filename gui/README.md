# G502 X Config (Wails GUI)

A minimal, experimental desktop front-end for `ratbagctl`, the command-line client bundled
with [libratbag](https://github.com/libratbag/libratbag). It exists so a G502 X can be
configured without typing `ratbagctl` commands by hand.

> **Status: builds and runs.** Verified on Ubuntu 26.04 with Go 1.26, Wails v2.16 and
> `libwebkit2gtk-4.1-dev`: `wails build -tags webkit2_41` produces `build/bin/gui`, which
> launches and lists libratbag devices. On distributions that still ship WebKitGTK 4.0, drop
> the tag.

## Prerequisites

- Go 1.25 or newer
- The Wails CLI v2:

  ```sh
  go install github.com/wailsapp/wails/v2/cmd/wails@latest
  ```

- Node.js and npm (for the Vite frontend build)
- Linux GUI development libraries:

  | Distribution         | Command                                                            |
  | -------------------- | ----------------------------------------------------------------- |
  | Ubuntu / Debian      | `sudo apt install libgtk-3-dev libwebkit2gtk-4.0-dev`             |
  | Fedora               | `sudo dnf install gtk3-devel webkit2gtk4.0-devel`                 |
  | Arch                 | `sudo pacman -S gtk3 webkit2gtk`                                 |

  Newer distributions no longer ship WebKitGTK 4.0. Install `libwebkit2gtk-4.1-dev` (Debian),
  `webkit2gtk4.1-devel` (Fedora) or `webkit2gtk-4.1` (Arch) instead, and pass the
  `webkit2_41` build tag.

## Develop

```sh
cd gui
wails dev
# or, on a distribution with WebKitGTK 4.1 only:
wails dev -tags webkit2_41
```

`wails dev` runs a Vite dev server for hot reload and exposes a browser dev server on
<http://localhost:34115> where the bound Go methods are also callable.

## Build

```sh
wails build
# or:
wails build -tags webkit2_41
```

The binary is written to `build/bin/`.

## How it works

- **`app.go`** — the backend. Exported methods are callable from JavaScript:
  - `RatbagctlAvailable()` — is `ratbagctl` on `PATH`?
  - `ListDevices()` — parses `ratbagctl list` into `{codename, name}` pairs.
  - `GetDeviceInfo(device)` — raw output of `ratbagctl <device> info`.
  - `SetDPI(device, profile, slot, dpi)` / `SetReportRate(device, profile, rate)` /
    `SetActiveProfile(device, profile)` — one `ratbagctl` write each.
  - Everything goes through `runRatbagctl`, which uses `os/exec` **without a shell**, so there
    is no command injection and a device name containing spaces is passed safely as one argument.
- **`frontend/`** — vanilla JavaScript + Vite. `src/main.js` renders the UI and calls the
  bindings; `wailsjs/` holds the generated bindings (regenerated by `wails dev` / `wails build`).
- Settings are stored in the mouse's onboard memory and applied immediately, matching
  `ratbagctl`'s default commit behaviour.

## Known limitations and next steps

- **Shelling out to `ratbagctl` is a stopgap.** It means parsing free-text output that libratbag
  makes no stability guarantee about. The robust upgrade is to talk to `ratbagd`'s D-Bus API
  directly (`github.com/godbus/dbus/v5`) — the same interface `ratbagctl` and Piper use.
- Only DPI, report rate and the active profile are exposed. Button mapping, a macro/shortcut
  builder, profile management and a clickable mouse map are the obvious next steps.
- The libratbag profile 0/1 quirk applies: after any write, click **Load info** and confirm the
  change landed on the profile you expected.
